# Best Practices for `AGENT.md` / `AGENTS.md`: Context Engineering & Software Design Discipline for AI Coding Agents

> **Scope & Primary Sources:** This document synthesizes primary industry standards and foundational software engineering literature into an operational blueprint for `AGENT.md` / `AGENTS.md` repository files. Every recommendation is anchored to primary sources: the [`AGENTS.md` Open Standard](https://agents.md/), Anthropic's [*Claude Code: Best practices for agentic coding*](https://www.anthropic.com/engineering/claude-code-best-practices), John Ousterhout's [*A Philosophy of Software Design* (2nd Ed., Yaknyam Press, 2021)](https://web.stanford.edu/~ouster/cgi-bin/book.php), Gergely Orosz's [*The Software Engineer's Guidebook* (2023) & *The Pragmatic Engineer*](https://www.pragmaticengineer.com/), Andrew Hunt & David Thomas's [*The Pragmatic Programmer* (20th Anniversary Ed., Addison-Wesley, 2019)](https://pragprog.com/titles/tpp20/the-pragmatic-programmer-20th-anniversary-edition/), Kent Beck's [*Tidy First?: A Personal Exercise in Empirical Software Design* (O'Reilly, 2023)](https://www.oreilly.com/library/view/tidy-first/9781098151232/), Simon Willison's [*Agentic Engineering Patterns* (2025–2026)](https://simonwillison.net/tags/agentic-engineering/), and [GitHub Docs: Repository Rulesets & Branch Protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

## 1. The `AGENT.md` / `AGENTS.md` Open Standard & Context Engineering

### 1.1 Cross-Agent Interoperability via Single Source of Truth (`AGENTS.md -> AGENT.md`)

As autonomous coding agents proliferated across CLI and IDE workflows, repository instructions fragmented across tool-specific files (`CLAUDE.md`, `.cursor/rules`, `.github/copilot-instructions.md`, `AGENT.md`, and `AGENTS.md`). The [`AGENTS.md` Open Standard](https://agents.md/)—supported across OpenAI Codex, Google Gemini / Antigravity, Cursor, Zed, and GitHub Copilot—establishes a single plain-Markdown specification at the repository root that acts as a **`README.md` for coding agents** ([`agents.md`](https://agents.md/)).

- **Zero Instruction Drift via Symlink (`AGENTS.md -> AGENT.md`):** Maintaining two separate instruction files inevitably violates the DRY principle ([Hunt & Thomas 2019, Topic 9](https://pragprog.com/titles/tpp20/the-pragmatic-programmer-20th-anniversary-edition/)). Keeping the canonical specification in `AGENT.md` and committing a POSIX relative symbolic link `AGENTS.md -> AGENT.md` ensures that agents scanning for either filename load the exact same byte-for-byte instructions.

### 1.2 Token-Budget Discipline ("Instruction Budget") & Verifiable Rules

In [*Claude Code: Best practices for agentic coding*](https://www.anthropic.com/engineering/claude-code-best-practices), Anthropic demonstrates that root instruction files are injected into the beginning of every agent session. Treating `AGENT.md` as a scarce **context-window budget** requires four structural rules:

1. **Command-First & Executable Over Vague Prose:** Replace aspirational adjectives (*"write clean, well-tested code"*) with exact, copy-pasteable verification commands (`npm test`, `npm run build:mac`, `npm run package:mac`) and expected exit codes ([`agents.md`](https://agents.md/); [Anthropic 2025](https://www.anthropic.com/engineering/claude-code-best-practices)).
2. **Tell the Agent What It Cannot Infer from Code Alone:** Document repository-specific invariants—such as the `next` (default integration) $\rightarrow$ `main` (production release) branch topology, zero-runtime-dependency constraints, and Web Audio synthesis rules—that cannot be guessed by reading a single source file ([Anthropic 2025](https://www.anthropic.com/engineering/claude-code-best-practices)).
3. **Architecture Map as a Table of Contents:** Provide a compact file-to-responsibility table (`src/timer-engine.js`, `src/storage.js`, `src/sound.js`, `src/notifications.js`, `src/app.js`, `macos/PomodoroApp.swift`) so the agent navigates directly to the right seam without burning context tokens grepping the entire workspace.
4. **Hard Guardrails Backed by Deterministic Checks:** Prompt instructions alone can degrade over long multi-step trajectories; every critical rule in `AGENT.md` must pair with a deterministic CLI verification gate (`npm test`, `git diff --cached` audit, and GitHub branch rulesets) ([Anthropic 2025](https://www.anthropic.com/engineering/claude-code-best-practices)).

## 2. Classic Software Engineering Literature Applied to AI Coding Agents

Because LLMs make *generating* lines of code nearly free, the primary failure mode of AI-assisted engineering is **uncontrolled complexity growth**—shallow pass-through wrappers, mixed refactoring/feature diffs, and tautological tests that confirm broken behavior. `AGENT.md` counteracts these failure modes by encoding principles from five foundational texts:

| Author & Primary Source | Core Principle | AI-Era Failure Mode Addressed | Actionable Rule Encoded in `AGENT.md` |
| :--- | :--- | :--- | :--- |
| **John Ousterhout**<br>[*A Philosophy of Software Design* (2nd Ed., 2021)](https://web.stanford.edu/~ouster/cgi-bin/book.php) | **Deep Modules** (Ch. 4), **Information Hiding** (Ch. 5), **Define Errors Out of Existence** (Ch. 10), **Design It Twice** (Ch. 11), & **Why-Comments** (Ch. 12–13). | Agents split cohesive logic into dozens of tiny "shallow" pass-through helpers (*classitis*), leak internal storage formats across modules, or add ad-hoc `if` patches (**tactical programming**). | - Prefer **deep modules**: small, simple public APIs hiding substantial internal work (`src/timer-engine.js`, `src/storage.js`, `src/sound.js`).<br>- Decompose by **abstraction**, never by arbitrary line-count rules.<br>- **Design It Twice** before committing to a load-bearing interface.<br>- **Define errors out of existence** where semantics allow; never swallow unexpected exceptions.<br>- Comments explain the non-obvious **why**, never restate the *what*. |
| **Gergely Orosz**<br>[*The Software Engineer's Guidebook* (2023) & *The Pragmatic Engineer*](https://www.pragmaticengineer.com/) | **Small, Focused PRs**, **Verification Over Generation**, **Risk-Stratified Review**, & **Operational Readiness**. | Agents emit 1,500-line multi-concern "AI slop PRs" that cause reviewer fatigue, rubber-stamping, and broken build/packaging pipelines. | - Keep every PR **small, single-purpose, and reviewable**.<br>- Shift effort from writing speed to **verification evidence** (automated tests + native `.app` build proof in PR body).<br>- Treat build scripts (`scripts/build-macos-app.sh`, `scripts/package-macos-release.sh`) and CI workflows as first-class production code. |
| **Andrew Hunt & David Thomas**<br>[*The Pragmatic Programmer* (20th Anniversary Ed., 2019)](https://pragprog.com/titles/tpp20/the-pragmatic-programmer-20th-anniversary-edition/) | **DRY** (Topic 9), **Orthogonality** (Topic 10), **Design by Contract** (Topic 23), & **No Broken Windows** (Topic 3). | Agents duplicate constants/versions across files, couple UI rendering to state-machine math, pass unvalidated inputs, or walk past stale comments. | - **DRY of domain knowledge:** Single source of truth for version (`package.json`) and timer ratios (`src/timer-engine.js`).<br>- **Orthogonality:** Pure state engine (`src/timer-engine.js`) has zero DOM or WebKit imports.<br>- **Design by Contract:** Validate preconditions up front with descriptive guard clauses; assert postconditions on critical outputs.<br>- **No Broken Windows:** Fix or update any stale comment or brittle test in the touched blast radius. |
| **Kent Beck**<br>[*Tidy First?* (O'Reilly, 2023)](https://www.oreilly.com/library/view/tidy-first/9781098151232/) | **Structural vs. Behavioral Separation** (*"Make the change easy, then make the change"*). | Agents tangle structural file/function reorganizations with behavioral bugfixes or features in one giant commit, making regressions impossible to bisect. | - **Never mix structural changes (tidying/refactoring) and behavioral changes (features/fixes) in the same commit.**<br>- If legacy code resists a change, land a pure behavior-preserving refactor commit first, then add the behavioral commit on top. |
| **Simon Willison**<br>[*Agentic Engineering Patterns* (2025–2026)](https://simonwillison.net/tags/agentic-engineering/) | **Red/Green TDD Loops for Agents**, **Deterministic Verification Gates**, & **Self-Contained Reproducers**. | Agents write implementation code first and then generate weak tests that merely assert what the buggy implementation already outputs. | - **Strict Red/Green TDD:** Write the automated test first in `tests/*.test.js`, run `npm test` to **watch it fail (Red)** for the expected reason, implement the minimal code to pass (**Green**), then refactor. |

## 3. Branching, PR Merge, & Security Guardrails (`next` → `main`)

An effective `AGENT.md` must explicitly govern how an autonomous agent interacts with Git, GitHub Pull Requests, and repository branches so that neither `next` nor `main` can be destabilized ([GitHub Docs: About the default branch](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-branches#about-the-default-branch); [GitHub Docs: About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)):

### 3.1 Mandatory Topic-Branch Workflow (`feat/*`, `fix/*` → `next` → `main`)

1. **Never Commit or Push Directly to `next` or `main`:**
   All agent work—whether a feature, bugfix, documentation update, or tidying refactor—**must** start by creating a descriptive topic branch off the latest `origin/next` (`git checkout -b <type>/<short-slug> origin/next`).
2. **`next` Is the Default Integration Branch; `main` Is the Production Release Branch:**
   - Every regular pull request targets **`next`** (`gh pr create --base next`).
   - Only verified release-promotion PRs (with an explicit Semantic Version bump in `package.json`) target **`main`** (`gh pr create --base main --head next`), which triggers `.github/workflows/release.yml` to build and publish `.dmg`, `.pkg`, `.zip`, and `SHA256SUMS.txt` to GitHub Releases.
3. **Merge Only via Pull Request After Green Verification:**
   - Before opening or merging any PR, the agent must run the full local verification gate (`npm test` and `npm run package:mac`), verify that GitHub Actions CI (`Test & Build Universal macOS App`) passes on the PR, and merge via PR (`gh pr merge --squash --delete-branch` for topic branches into `next`; `--merge` for release promotions from `next` into `main`).

### 3.2 Pre-Commit & Pre-PR Security Hygiene

Before every `git commit` and `gh pr create`, the agent must run a staged-diff audit (`git diff --cached`) to guarantee:
- **Zero Secrets or Credentials:** No API keys, tokens, Developer ID certificates (`.p12`), or keychain profiles are ever staged.
- **Zero Personal Machine Paths or Stale Codename Leakage:** No local home-directory paths or legacy internal codenames appear anywhere in code, tests, docs, commit messages, or PR descriptions.
- **Clean Artifact Boundary:** Build outputs (`dist/`, `build/`, `*.dmg`, `*.pkg`, `*.zip`, `.DS_Store`) remain gitignored and are published exclusively via GitHub Releases.
